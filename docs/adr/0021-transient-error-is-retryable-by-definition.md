# TransientError is retryable by definition

Status: active

`ar` decided whether a classified provider failure was retryable by comparing a free-text marker on the failure value: `reduce_text_output_events` surfaced `TransientError` as a retryable `ProviderUnavailableError` only when `TransientError.classification == "retryable"`, and as a `HardAgentError` otherwise. Four of the five sites that construct `TransientError` never set that marker, so genuine server-side failures — every Claude 5xx, every Codex 5xx, every OpenCode 5xx, and the status-less variants — surfaced to consumers as non-retryable hard errors. A consuming project reported a Claude `api_error_status: 500` (`"API Error: 500 Internal server error. This is a server-side issue, usually temporary"`) arriving as `HardAgentError`.

The marker was a category error. `Built-in Provider Parsed Output` already decides retryability by **choosing a type**: each per-service classifier discriminates 5xx from 4xx and maps them to `TransientError` and `HardError` respectively. The classification gate then re-litigated that decision with a weaker, opt-in signal, and the majority of call sites did not participate. We make the type the sole carrier of the verdict: `TransientError` means retryable, `HardError` means it is not.

## Considered Options

- **Tag the four silent construction sites** with `classification="retryable"`. Rejected: it preserves a gate whose only correct answer is "yes", and the next parser author who omits the string reintroduces this exact bug. The failure mode is silent and consumer-visible.
- **Treat `TransientError` as a raw observation** and keep the gate as the verdict. Rejected: the type is then misnamed, and no construction site in the codebase produces a non-retryable one. The only value other than `"retryable"` that has ever existed is `"permanent"`, invented by the gate's own unit test.
- **Delete the gate; `TransientError` always surfaces as `ProviderUnavailableError`.** `classification` is removed from the `TransientError` contract, since nothing reads it once the gate is gone. Accepted.

## Consequences

- This refines ADR 0020. That ADR's core decision stands — `TransientAgentError` is retired, and `status_code` stays off `ar`'s exception surface. What is voided is its closing claim that "the retryable `TransientError` path (`classification="retryable"` → `ProviderUnavailableError`) is unchanged", and the second half of its title: there are no non-retryable transient signals, because the category is empty. ADR 0020's reasoning correctly identified that a non-retryable transient signal is incoherent, then kept the gate instead of concluding the category was empty — it is preserved unedited as the record of that error.
- Five provider signals move from raising `HardAgentError` to returning `RuntimeOutcome(kind=ProviderUnavailable, reason=TRANSIENT_API_ERROR)`: Claude 5xx, Claude `is_error` result with no `api_error_status`, Codex message reporting `status` ≥ 500, OpenCode `statusCode` ≥ 500, and OpenCode error with no `statusCode` that is not `"model not found:"`. This is a breaking change for consumers: code that caught `HardAgentError` for these now takes the normal-return path and must handle the outcome.
- `TransientError.classification` is deleted from `contracts.py`. Codex's "selected model is at capacity" classifier drops the now-redundant argument. Should we later need to distinguish *why* something is retryable, the home for that is a new variant on the closed public `ProviderUnavailableReason` enum, not a free-text string on an internal contract.
- The per-service disagreement about **status-less** failures is deliberately left in place: Claude and OpenCode classify an unidentifiable failure as `TransientError`, while Codex classifies it as `HardError(status_code=500)` — a fabricated status on the hard type, one branch away from treating an observed 500 as transient. Aligning them without captured evidence of what each provider actually emits would trade one known bug for three unknown ones. `Built-in Provider Parsed Output` owns provider-specific classification, so divergence is within its remit until real cases justify a decision.
- Accepted risk: a *deterministic* Claude or OpenCode failure that arrives without a status now reads as retryable, so a consumer's retry policy may loop on it. Chosen knowingly over guessing at a classification rule; real occurrences are expected to surface and drive a follow-up decision.
